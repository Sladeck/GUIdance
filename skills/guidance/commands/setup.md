# `/guidance setup`

Write nothing before the user answers "apply" to step 8. This holds even when one reply answered every question or said to take your recommendations: answers to steps 4 and 5 are choices, not the go-ahead. Never offer to go ahead if the user does not answer.

**A. Understand the project.** Read, do not guess:
1. Find the project root and work out where styling lives, whatever the stack: a global stylesheet, a Tailwind entry CSS, a theme object (`createTheme`, a Chakra or Mantine theme), Sass variables, a component library's variables (shadcn's `--primary`, Bootstrap's `$primary`), or native theme code (SwiftUI asset catalog or `Color` extension, Compose `ColorScheme`, Flutter `ThemeData`, React Native theme). Tokens go where the project already defines styling, in its own format and naming. `references/data/stacks.md` lists traps for common stacks (MUI, Tailwind, shadcn, Bootstrap, Jetpack Compose, SwiftUI); read only your stack's section before writing.
2. List the existing tokens: CSS custom properties, Sass variables, theme objects and token files (`tokens.ts`, `theme.ts`, `*.tokens.json`). A `:root` block of custom properties in a stylesheet is a token source, even with only a few variables and no file named tokens; so is a Sass partial of variables. Follow aliases (`$space-sm: var(--x-space-sm)`) to the real value and the file that defines it. Compare spacing, radius, type and durations with `references/data/scales/spacing-density.md`, `references/data/scales/shape.md`, `references/data/scales/type.md` and `references/data/scales/motion.md`, and note each off-scale value with its nearest scale value. Read those four files before judging any value: never judge from memory. Convert units first (`.35s` is 350ms, `1rem` is 16px); a value in the file's list is on the scale and is not reported. Look at every value in use, not only the tokens: raw values in stylesheets, component files and inline styles count. Group near-identical colours (greys or tints a few steps apart, such as `#333`, `#343434` and `#323232`) as one role (rule 4.5).
3. Learn what the product is from the README, PRODUCT.md or DESIGN.md, the package description, page titles and metadata. Collect brand colours: tokens named brand, primary, accent or main, and colours in logo or favicon SVGs.
4. Tell the user in a few lines what you found. If the product, its users or the brand are unclear, ask in one question set: what it is, who uses it, the feel (calm, bold, playful, serious, premium), light or dark first, any brand colour. Skip what the project already answered. Then show the choice table of `commands/spacing.md` step 2 if the project has no density role tokens, and that of `commands/shape.md` step 2 if it has no radius role tokens (one row per role, the presets as columns, the recommended preset named with its reason); the user answers in one reply; risky picks are explained and confirmed as in step 3 of those commands. A reply that picks no preset gets the one whose "Use for" row fits the product. If the project has a token source with off-scale values (step 2), ask in the same question set which to move (multi-select), because moving radius or durations changes how the app looks. A project that already has role tokens keeps them: state its current density and shape and point to `/guidance spacing` and `/guidance shape` to change them.

**B. Colours** (if the user keeps their colours, skip steps 5 and 6 and run step 7 on the colours they have)
5. Show the choices as a table and wait for the answer, each with its reason and source from `references/data/colour/building.md`:
   - surfaces: near-grey (recommended for products: Primer, Carbon and Radix all do it) or tinted with the brand hue (expressive, brand-heavy products);
   - accents: one accent, or a second brighter one for a single kind of highlight;
   - the brand colour's role: `primary` or `primary-container`, decided by its luminance. Say which and why.
   Mood words ("calm", "playful") are judgment: say so.
6. Build the colour roles for light and dark as `references/data/colour/building.md` describes. Never invent a role name: use the Material roles, plus `success`, `warning` and `chart-1` to `chart-5` (GUIdance additions, see `references/data/colour/roles-tones.md`).
7. Check every pair by hand with the contrast formula and show the result: role, light value, dark value, then each pair with its ratio and the threshold it must reach. Fix a failing pair before showing the set as final. Say that the ratios are computed by hand and which pairs sit close to their threshold.
8. Show what will be written: each file to create or edit, the values that change (off-scale moves included), the categories and roles added, and the wiring line. Anything outside the token source and the wiring line (component styles, raw values swapped for roles) is its own item in that list. Then ask: apply, adjust, or stop. Stop there until the user answers; write only what they accepted. A colour the user insists on that fails its pair is a risk: say which text becomes hard to read and for whom (WCAG 1.4.3, Level AA), and apply it only if they confirm. Record it in the token file.

**C. Write the tokens**
9. **Project already has tokens** (any token source from step 2, however small). Do not add a parallel set.
   - Write into that source: the `:root` block, partial or theme object where they are defined. Do not create a new token file, and do not delete or rename the existing tokens; they become the roles they match.
   - Off-scale values: move only the ones the user picked in step 4.
   - Edit values where they are defined: the token source file, not aliases.
   - Add only the categories that are missing, in the project's naming.
   - Density role tokens count as a missing category when the project has none (step 4). Take them from `references/data/scales/spacing-density.md` for the density picked in step 4, point them at the project's own spacing tokens, and apply them as `commands/spacing.md` step 4 says (touch floor, phone widths, compact).
   - Radius role tokens count as one too, on the same condition. Take them from the Shape presets in `references/data/scales/shape.md` for the shape picked in step 4, and apply them as `commands/shape.md` step 4 says.
   - Colours: map the roles of the colour set onto the existing colour names where they match, and add the rest.
10. **No token system yet.** Create one token file in the stack's own format, next to where styling lives.
    - Model: `references/formats/` has complete worked examples for plain CSS, Tailwind v4 and v3, MUI, Sass, SwiftUI and Jetpack Compose. Use the closest one for names, sections and dark-mode wiring, and translate it for other stacks.
    - Categories: spacing, density roles, radius, radius roles, elevation, type, motion, targets, focus, and the colour roles for light and dark from step 6. Values come from `references/data/scales/spacing-density.md`, `references/data/scales/shape.md`, `references/data/scales/elevation.md`, `references/data/scales/type.md`, `references/data/scales/motion.md` and `references/data/accessibility.md`.
    - Density roles: the examples carry the default density with its phone-width values (CSS variables in the CSS, Sass and Tailwind v4 examples; separate phone keys in the Tailwind v3 and MUI ones; a wide variant in the SwiftUI and Compose ones). For another preset, repoint them and update the `density:` note. In every case, the default density included, apply `commands/spacing.md` step 4 (touch floor, phone widths, compact).
    - Radius roles: the examples carry the soft shape. For another shape, repoint them and update the `shape:` note, as `commands/shape.md` step 4 says.
    - The file and the wiring line are shown in step 8. Never overwrite an existing file. Then add the wiring line to the project's entry file.
11. Put a short comment in the token file recording the brand colour, the choices of step 5 and any accepted risk.
12. Check by reading the file you wrote: every role has a light and a dark value, every pair of step 7 still holds, and no value is off its scale.
13. Finish with what changed (files and values) and what to verify visually. Do not commit.
