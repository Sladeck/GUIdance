# `/guidance setup`

**A. Understand the project.** Read, do not guess:
1. Find the project root and work out where styling lives, whatever the stack: a global stylesheet, a Tailwind entry CSS, a theme object (`createTheme`, a Chakra or Mantine theme), Sass variables, a component library's variables (shadcn's `--primary`, Bootstrap's `$primary`), or native theme code (SwiftUI asset catalog or `Color` extension, Compose `ColorScheme`, Flutter `ThemeData`, React Native theme). Tokens go where the project already defines styling, in its own format and naming. `references/data/stacks.md` lists traps for common stacks (MUI, Tailwind, shadcn, Bootstrap, Jetpack Compose, SwiftUI); read only your stack's section before writing.
2. List the existing tokens: CSS custom properties, Sass variables, theme objects and token files (`tokens.ts`, `theme.ts`, `*.tokens.json`). Follow aliases (`$space-sm: var(--x-space-sm)`) to the real value and the file that defines it. Compare spacing, radius, type and durations with `references/data/scales.md`, and note each off-scale value with its nearest scale value.
3. Learn what the product is from the README, PRODUCT.md or DESIGN.md, the package description, page titles and metadata. Collect brand colours: tokens named brand, primary, accent or main, and colours in logo or favicon SVGs.
4. Tell the user in a few lines what you found. If the product, its users or the brand are unclear, ask in one question set: what it is, who uses it, the feel (calm, bold, playful, serious, premium), light or dark first, any brand colour. Skip what the project already answered. Then show the choice table of `commands/spacing.md` step 2 if the project has no density role tokens, and that of `commands/shape.md` step 2 if it has no radius role tokens (one row per role, the presets as columns, the recommended preset named with its reason); the user answers in one reply; risky picks are explained and confirmed as in step 3 of those commands. With no answer, use the preset whose "Use for" row fits the product. A project that already has role tokens keeps them: state its current density and shape and point to `/guidance spacing` and `/guidance shape` to change them.

**B. Colours** (skip if the user keeps their colours; then only run step 7 on the colours they have)
5. Show the choices as a table and wait for the answer, each with its reason and source from `references/data/colour.md`:
   - surfaces: near-grey (recommended for products: Primer, Carbon and Radix all do it) or tinted with the brand hue (expressive, brand-heavy products);
   - accents: one accent, or a second brighter one for a single kind of highlight;
   - the brand colour's role: `primary` or `primary-container`, decided by its luminance. Say which and why.
   Mood words ("calm", "playful") are judgment: say so.
6. Build the colour roles for light and dark as "Building a colour set from a brand colour" describes. Never invent a role name: use the Material roles, plus `success`, `warning` and `chart-1` to `chart-5` (GUIdance additions, see `references/data/colour.md`).
7. Check every pair by hand with the contrast formula and show the result: role, light value, dark value, then each pair with its ratio and the threshold it must reach. Fix a failing pair before showing the set as final. Say that the ratios are computed by hand and which pairs sit close to their threshold.
8. Ask: apply, adjust, or stop. A colour the user insists on that fails its pair is a risk: say which text becomes hard to read and for whom (WCAG 1.4.3, Level AA), and apply it only if they confirm. Record it in the token file.

**C. Write the tokens**
9. **Project already has tokens**: do not add a parallel set. List off-scale values with their nearest scale value and ask which to move (one question, multi-select): moving radius or durations changes how the app looks. Edit values where they are defined (the token source file, not aliases). Add only missing categories, following the project's naming; the density role tokens count as one (Density section of `references/data/scales.md`, pointing at the project's own spacing tokens), for the density picked in step 4, applied as in `commands/spacing.md` step 4 with its touch floor, phone-width and compact bullets. For the colour set, map its roles onto existing colour names where they match and add the rest. The radius role tokens count as a missing category too (Shape presets in `references/data/scales.md`), for the shape picked in step 4, applied as in `commands/shape.md` step 4.
10. **No token system yet**: create one token file in the stack's own format, next to where styling lives, with every category: spacing, the density role tokens for the density picked in step 4 (Density section of `references/data/scales.md`; the worked examples carry them for the default density, with the phone-width values (as CSS variables in the CSS, Sass and Tailwind v4 examples, as separate phone keys in the Tailwind v3 and MUI ones): repoint them for another preset and update the `density:` note, applied as in `commands/spacing.md` step 4 with its touch floor, phone-width and compact bullets), radius, elevation, type, motion, targets, focus and the colour roles for light and dark from step 6 (the other values from `references/data/scales.md`). `references/formats/` has complete worked examples for plain CSS, Tailwind v4 and v3, MUI, Sass, SwiftUI and Jetpack Compose: use the closest one as the model (names, sections, dark-mode wiring) and translate it for other stacks. Show the file and the wiring line before writing; never overwrite an existing file. Then add the wiring line to their entry file. The worked examples carry the radius role tokens for the soft shape: repoint them for the shape picked in step 4 and update the `shape:` note, as in `commands/shape.md` step 4.
11. Put a short comment in the token file recording the brand colour, the choices of step 5 and any accepted risk.
12. Check by reading the file you wrote: every role has a light and a dark value, every pair of step 7 still holds, and no value is off its scale.
13. Finish with what changed (files and values) and what to verify visually. Do not commit.
