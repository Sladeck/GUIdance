# `/guidance build <what>`

1. Find the rules relevant to what you are building in the index, `references/rules.md`, and read their section files in `references/rules/`. Do not apply all of it for a one-component change.
2. Use the project's design system (tokens, DESIGN.md, theme file). The rules set floors and ratios, not a brand. Only flag a project value when it breaks a **Hard** rule. Then say so before building and ask: fix it at the token (one change, every screen that uses it moves) or build with it as it is. Never work around a failing token with raw values in the new code: the new screen drifts from the system and the token stays broken everywhere else. If the project has no tokens, suggest `/guidance setup` once, then build with the values in `references/data/scales/`.
3. Express decisions as tokens (spacing, radius, type scale, durations), never one-off raw values. When the project has spacing role tokens (`space-field`, `space-group`, `space-section`, see rule 4.7), use the role, not the scale step, so the screen follows the project's density. The same goes for radius roles (`radius-button`, `radius-card`, see rule 5.5).
4. After building, go through the checklist in `commands/review.md` on what you made and fix what fails. This step is not optional, even for a small component. In the finish, name the checklist sections you checked, what you fixed, and what you could not check without a browser (contrast computed by hand, widths, dark mode).
5. When the user asks for something a rule advises against (12px body text, a 20px tap target, a colour that fails contrast), say so before building it: the rule, its source and tier, what goes wrong for people, and the nearest value that follows the rule. Then ask. A Hard rule (a WCAG requirement) is not built broken without that explicit yes. Finish with what you built and the rules the user chose to break, each with its reason.
