# `/guidance setup`

Write nothing before the user answers "apply" to step 8. This holds even when one reply answered every question or said to take your recommendations: answers to steps 4 and 5 are choices, not the go-ahead. Never offer to go ahead if the user does not answer.

**A. Understand the project.** Read, do not guess:
1. Find where styling lives and list the existing tokens, as `commands/find-tokens.md` says.
2. Compare spacing, radius, type and durations with `references/data/scales/spacing-density.md`, `references/data/scales/shape.md`, `references/data/scales/type.md` and `references/data/scales/motion.md`, and note each off-scale value with its nearest scale value. Read those four files before judging any value: never judge from memory. A value in the scale file's list is on the scale and is not reported. Note the design language the project follows (Material through MUI, Apple HIG in SwiftUI, Fluent, a house style) and which themes exist: light, dark, and how dark is switched. Name every colour source, including a module of colour constants (`colors.ts`, a Sass map), a second set under `prefers-color-scheme` or a dark class, and a starter template's leftovers (create-next-app's `--background` and `--foreground`). Group near-identical colours (greys or tints a few steps apart, such as `#333`, `#343434` and `#323232`) as one role (rule 4.5).
3. Learn what the product is from the README, PRODUCT.md or DESIGN.md, the package description, page titles and metadata. Collect brand colours: tokens named brand, primary, accent or main, and colours in logo or favicon SVGs.
4. Tell the user in a few lines what you found. If the product, its users or the brand are unclear, ask in one question set: what it is, who uses it, the feel (calm, bold, playful, serious, premium), any brand colour. Skip what the project already answered. Whether or not anything was unclear, a project with one theme gets the theme question in that set: with no dark mode, whether to add one; with dark only, whether to add light; and which is the default. Recommend both (rule 1.5, Strong); a theme the user declines goes on the record's Accepted risks line. Then show the choice table of `commands/spacing.md` step 2 if the project has no density role tokens, and that of `commands/shape.md` step 2 if it has no radius role tokens (one row per role, the presets as columns, the recommended preset named with its reason); the user answers in one reply; risky picks are explained and confirmed as in step 3 of those commands. A reply that picks no preset gets the one whose "Use for" row fits the product. If the project has a token source with off-scale values (step 2), ask in the same question set which to move (multi-select), because moving radius or durations changes how the app looks. A project that already has role tokens keeps them: state its current density and shape and point to `/guidance spacing` and `/guidance shape` to change them.

**B. Colours** (if the user keeps their colours, skip steps 5 and 6 and run step 7 on the colours they have)
5. Show the choices as a table and wait for the answer, each with its reason and source from `references/data/colour/building.md`:
   - surfaces: near-grey (recommended for products: Primer, Carbon and Radix all do it) or tinted with the brand hue (expressive, brand-heavy products);
   - accents: one accent, or a second brighter one for a single kind of highlight;
   - the brand colour's role: `primary` or `primary-container`, decided by its luminance. Say which and why.
   Mood words ("calm", "playful") are judgment: say so.
6. Build the colour roles for each theme the product will have (light, dark or both, step 4) as `references/data/colour/building.md` describes. Never invent a role name: use the Material roles, plus `success`, `warning` and `chart-1` to `chart-5` (GUIdance additions, see `references/data/colour/roles-tones.md`).
7. Check every pair by hand with the contrast formula and show the result: role and its value in each theme, then each pair with its ratio and the threshold it must reach. Fix a failing pair before showing the set as final. Say that the ratios are computed by hand and which pairs sit close to their threshold.
8. Show what will be written: each file to create or edit, the values that change (off-scale moves included), the categories and roles added, the wiring line, and the decisions record (`references/formats/decisions.md`) with its lines filled in, or the lines that change if it exists. The dark-mode work of step 9 (a dark copy folded in, its switch rewired) is listed with the token changes, file by file, not as an optional item. Anything else outside the token source and the wiring line (component styles, raw values swapped for roles) is its own item in that list. Then ask: apply, adjust, or stop. Stop there until the user answers; write only what they accepted. A colour the user insists on that fails its pair is a risk: say which text becomes hard to read and for whom (WCAG 1.4.3, Level AA), and apply it only if they confirm. Record it on the Accepted risks line of the decisions record.

**C. Write the tokens**
9. **Project already has tokens** (any token source from step 1, however small). Do not add a parallel set.
   - Write into that source: the `:root` block, partial or theme object where they are defined. Do not create a new token file, and do not delete or rename the existing tokens; they become the roles they match.
   - Off-scale values: move only the ones the user picked in step 4.
   - Edit values where they are defined: the token source file, not aliases.
   - Add only the categories that are missing, in the project's naming.
   - Density role tokens count as a missing category when the project has none (step 4). Take them from `references/data/scales/spacing-density.md` for the density picked in step 4, point them at the project's own spacing tokens, and apply them as `commands/spacing.md` step 4 says (touch floor, phone widths, compact).
   - Radius role tokens count as one too, on the same condition. Take them from the Shape presets in `references/data/scales/shape.md` for the shape picked in step 4, and apply them as `commands/shape.md` step 4 says.
   - Colours: map the roles of the colour set onto the existing colour names where they match, and add the rest. Write each value once: where an existing name holds a role's value, one points at the other (`--color-primary: var(--main-color)`), never a second copy of the hex. Colour constants outside the token source count (a `colors.ts`, a Sass map, a Swift `static let`): each points at its role, which also makes it follow dark mode (MUI: `MUTED = 'var(--mui-palette-text-secondary)'`, which needs `cssVariables` in the theme; add it in the plan if missing). Check each use first. Where one needs a literal value (canvas, a chart library, colour maths) or the theme itself imports the constant (MUI's `palette` needs literal colours, `references/data/stacks.md`), keep the hex there as the one source and list the components that read it, to move to the theme's roles.
   - Dark mode the project already has (a dark theme object, a dark class or `[data-theme]` block, a `prefers-color-scheme` set): the dark roles replace its colours as part of the plan, not an opt-in item, and the app must end up showing them (when the user keeps their colours, its dark colours stay and step 7 checks them). A dark copy that redefines the theme (its own spacing, radius or overrides) folds into the one theme's dark scheme, with its switch rewired (MUI: `colorSchemes` and `useColorScheme`). Two dark sets (a starter template's `prefers-color-scheme` beside a toggle) become one. An existing colour name that components read, constants included, becomes mode-aware where the stack allows (a variable the dark set redefines); where it cannot, say in the finish which components stay light in dark mode. With no dark mode in the project, adding one is the user's choice (step 4).
10. **No token system yet.** Create one token file in the stack's own format, next to where styling lives.
    - Model: `references/formats/` has complete worked examples for plain CSS, Tailwind v4 and v3, MUI, Sass, SwiftUI and Jetpack Compose. Use the closest one for names, sections and dark-mode wiring, and translate it for other stacks.
    - Categories: spacing, density roles, radius, radius roles, elevation, type, motion, targets, focus, and the colour roles from step 6 (leave out the example's dark set when the product has no dark theme). Values come from `references/data/scales/spacing-density.md`, `references/data/scales/shape.md`, `references/data/scales/elevation.md`, `references/data/scales/type.md`, `references/data/scales/motion.md` and `references/data/accessibility.md`.
    - Density roles: the examples carry the default density with its phone-width values (CSS variables in the CSS, Sass and Tailwind v4 examples; separate phone keys in the Tailwind v3 and MUI ones; a wide variant in the SwiftUI and Compose ones). For another preset, repoint them. In every case, the default density included, apply `commands/spacing.md` step 4 (touch floor, phone widths, compact).
    - Radius roles: the examples carry the soft shape. For another shape, repoint them, as `commands/shape.md` step 4 says.
    - The file and the wiring line are shown in step 8. Never overwrite an existing file. Then add the wiring line to the project's entry file.
11. Write the decisions record, `design-decisions.md` at the project root, as `references/formats/decisions.md` describes: every decision found in steps 1 and 2 or made in steps 4 and 5, and any accepted risk, keeping the lines of an existing record that this run did not change. In the token file, one comment line points at it; an older `density:` or `shape:` comment there moves into the record.
12. Check by reading the file you wrote: every role has a value in each theme the product has, every pair of step 7 still holds, no value is off its scale, and every value written is the one the plan of step 8 showed. Then check each value you called off-scale in step 2: it must be missing from its scale file's list. If it is there, say so in the finish and undo that move.
13. Finish with what changed (files and values) and what to verify visually. Do not commit.
